Phase 1 — The inverted index + boolean AND

Invert doc→words into term→docs (the posting list) at build time, and "which docs contain shoes?" becomes instant. A boolean AND query just intersects the posting lists.

Intersection → matching docs

The index found candidates fast; it did not rank them. AND says which docs match, not which match best. That's the next two phases.

Phase 2 — TF-IDF ranking

A results page needs an order. score = Σ TF(term) × IDF(term) — a rare word (IDF = log(N/df)) that appears several times in a doc drives the ranking.

Ranked results · click a row for the per-term math

TF-IDF has two flaws BM25 fixes next: TF grows without limit (keyword-stuffable), and it doesn't normalize for length so long docs win unfairly.

Phase 3 — BM25 vs the two flaws

Phase 7 — Phrase & positional queries

Boolean AND finds docs with the words anywhere. A phrase query needs them adjacent, in order — only possible because the index also stored each term's positions. It's why "new york" must not match a doc that says "york, new".

Phase 8 — Fuzzy matching & spelling correction

A search box that returns nothing for resturant is failing at the vocabulary boundary, not at ranking. Typo tolerance is query-side repair: find the real index term within a small edit distance, correct the query, then search.

2

Results after correct → analyze → search

Edit distance is the centerpiece: levenshtein("shoez","shoes") = 1. Brute-forcing it over a whole vocabulary is O(vocab × len²) — at scale you prefilter with trigram indexes, BK-trees, SymSpell, or Levenshtein automata.

Phase 9 — Vector / semantic search

Lexical search matches characters; it's blind to meaning — sneakers never matches shoes. Semantic search embeds docs and the query into vectors and ranks by cosine similarity, so meaning matches even when words don't.

Semantic ranking (cosine) · vs. raw lexical overlap

Phase 10 — Hybrid search + Reciprocal Rank Fusion

Lexical and semantic retrieval each miss what the other catches. Run both, then fuse with RRF: score(d) = Σ 1/(k + rank). It uses only ranks, so BM25 and cosine scores never have to be normalized onto the same scale.

Phase 11 — Learning to Rank

Phase 4 guessed the re-rank weights. LTR learns them from judgments. The pairwise trick: turn "doc A should beat doc B" into a training pair and nudge a weight vector until w·features(A) > w·features(B) for every pair.

Phase 5 — Scatter-gather & tail latency

Shard by document, scatter the query to every shard, gather their local top-k. The tax: the query is only as fast as the slowest shard — and more shards means a worse tail.

5 shards — shard 3 is having a bad moment (300ms)

—wall-clock
Naive waits for all shards → bound by the 300ms laggard. Hedging re-sends the laggard to a replica after 50ms and takes whichever answers first.

Why p99 gets worse as you scale out

If a single shard is slow just 1% of the time, the chance a query touches at least one slow shard is 1 − 0.99^S:

ShardsP(query hits ≥1 slow shard)
More shards = better throughput but worse tail. Hedging & early-termination are how you claw p99 back. This is the defining operational fact of scatter-gather.

Phase 6 — Typeahead (precomputed prefixes)

Suggestions must appear in <50ms — no time to search per keystroke. So it's a build-time problem: precompute top-K completions per prefix. Query time is one O(1) point lookup, no ranking.

Built 0 prefixes offline from a 12-query log. Each keystroke is a hash hit on that table — nothing is ranked online. Production layers a client-side debounce/cache (tier zero) and a trending lane gated by k-distinct-users on top.
